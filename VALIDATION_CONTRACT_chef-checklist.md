**Findings**
1. **HIGH, api.mjs:260 (ckNotes).** When a GHL notes read fails, the result is `[]` (or the old copy), and the `[]` is cached for 5 minutes as if it were real. A harness proved it: the read failed once, and a second read 1 s later with GHL healthy still returned `[]` without calling GHL. The effect: on a 429 during a fresh=1 build (about 20 contacts read with 4 in parallel, alongside the snapshot's own GHL burst), a chef with a sign-up card shows "The sign-up came in but no welcome email is on record. Tell Jay." The bgcheck, W-9 and Gusto steps revert the same way, and the page carries no warning. **Fix:** on failure, do not cache. Set a flag (`stale.ghl = true`) and have the UI show "GoHighLevel did not answer, some steps may be out of date". Better, have ckChef keep the previous state for that chef.
2. **HIGH, api.mjs:324-325 (ckInputs).** A failed contractor-cards search becomes `{opportunities: []}`, and a failed Assigned Chef field read becomes `{}`, with no flag. If the field read fails, all 18 chefs show "Missing from the GoHighLevel Assigned Chef list. Tell Jay." If the cards search fails, every new chef's sign-up form changes to "Started before the sign-up form", the order breaks (C-2), and chefs who exist only as a card vanish. The bad result is then cached in mem.ckIn and mem.ckOut for 2 minutes. **Fix:** let these failures throw (an honest 502, which the UI already handles), or return `stale.ghl` and leave the dependent steps unchanged.
3. **MED, api.mjs:277 + 288 (ckSignwell).** On a non-OK list call (429 under the 5-per-30 s limit) or a failed direct read, `stale = true`, but `ck:sw` is still rewritten with `at: now`. For the next 10 minutes, every non-fresh GET on any instance returns `stale: false` from that failed refresh, so the "SignWell status may be out of date" banner disappears while the data is still old. A harness proved it: a 15-minute-old cache plus a 429 gave stale=true on call 1, then stale=false with no SignWell call on call 2. Two or three Refresh taps within 30 s (Amber and Jay together) are enough to trigger it, because fresh=1 always makes 1 or 2 list calls and nothing throttles that. **Fix:** when stale, keep the old `at` and write only new docs, or store `{stale: true}` and return it. Also skip the list call on fresh=1 when the last list call was under 30 s ago (store `lastList` in the blob).
4. **MED, api.mjs:276, 285, 296 and ghl() at 61.** None of these fetches has a timeout or AbortSignal. A slow nutritionintuitionaz.com (fetched on every fresh=1 and hourly), a stalled SignWell call or a stuck GHL call holds the whole GET until Netlify kills it at about 10 s, and the tab shows "Could not load the checklist". The same applies to the POST's ckBuild: the tick is saved to Blobs before the note, so a kill between the two leaves a tick without its GHL note (see 6). **Fix:** `signal: AbortSignal.timeout(3000)` on the SignWell and website fetches (falling back to the cache, which already exists) and about 6 s on ghl().
5. **MED, api.mjs:244 + 339 (tick key = slug of the display name).** Ticks are stored under `ckSlug(name)`. The checklist itself tells Amber to get name spellings fixed: for Viana it says "GoHighLevel spells the name "Viana Nguyen", the app "Viana Nyguen". Tell Jay which is right." If Jay corrects cfg.chefs, the id changes from viana-nyguen to viana-nguyen, and every tick Amber made for Viana silently disappears. The orphaned ticks stay in the blob and the UI never shows them. The same happens when a tag-sourced lowercase name is later added to cfg.chefs with a different spelling. **Fix:** key ticks by the chef's primary email (it is already the identity in ckRoster, "matched by email, never by name") or by contactId. Or keep an alias map and migrate on read.
6. **LOW, api.mjs:797 + 802 (note not retried).** If the GHL note fails, the response is ok with note:false, and the UI honestly says "The GoHighLevel note did not go through." But a repeat tick returns `unchanged` before the note step, so there is no way to get the missing note written, and the CRM mirror (global rule 1) is permanently missing that tick. **Fix:** store `noted: false` on the tick, and on `unchanged` retry the note while `noted` is false.
7. **LOW, api.mjs:782.** A `null` JSON body passes `req.json().catch(() => ({}))` as null, and `b.chefId` throws. The outer catch then answers 502 with the internal error text. **Fix:** `const b = (await req.json().catch(() => null)) || {}`, plus `typeof b === 'object'`.
8. **LOW, api.mjs:785-790 (auto-done steps accept ticks).** The API checks only CK_MANUAL membership, not the step's current state. A POST of `packet` / `agreement` / `agreementSent` for a chef whose step is already AUTO-done (Angelica's welcome email, for example) is saved and writes a "marked done" note on the real contact. The screen does not change, and because canUndo is only true for `via: 'tick'`, Amber cannot remove the stray tick from the UI. The UI hides the button, so this takes a stale screen, the toast Undo or a direct call. **Fix:** reject with 409 "already done automatically" when `chef.steps[step].state === 'done' && via !== 'tick'` (expose `via` or `canUndo`).
9. **MED (C-5 coverage gap), api.mjs:482.** The fixture chef is built with `contacts: []` and `gusto: []`, so the checklist never reads the ZZTEST contact's notes. Make 6642770 wrote "GUSTO HAND-OFF SENT (chef agreement signed) / Sent to: ..." on W4UfXxOmRlkMBUwZkg0f at 09:28:19Z, but the ZZTEST checklist still showed Gusto "To do". So the AUTO Gusto path (api.mjs:476-477, and the packet path) has never been exercised end to end in the app. I checked the regex offline against that real note: the marker matched and the `Sent to:` email parsed correctly. **Fix:** in test mode, read `ckNotes(cfg.testChefContact)` and feed its packets and gusto notes into the fixture. Then re-run the hand-off fixture and confirm the step shows "Emailed Oct 15 to ... so finance can add ZZTEST in Gusto."
10. **LOW, api.mjs:459 (per-instance mem.ckOut).** Each function instance caches the built list, ticks included, for up to 2 minutes (the life of mem.ckIn). A tick made on one instance is not seen by a GET on another warm instance until then, so a second phone can show the old state. The POST response updates the phone that ticked. **Fix:** re-read `chefcheck` (one strong read) on every GET and merge it over the cached evidence, instead of caching ticks inside mem.ckOut.
11. **LOW, cosmetic.** Undoing a "sent" step writes "marked not done (undo)" where "marked not sent (undo)" is meant (api.mjs:801). In test mode, `summary.todo` / `waiting` count the ZZTEST chef while `summary.chefs` excludes it (api.mjs:490). In the UI, a Refresh tap made while a normal load is running is silently dropped (index.html:822).
